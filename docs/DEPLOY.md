# Putting it on Render, for testing

Production is still Vercel (CLAUDE.md). This is a hosted environment to put in
front of people — a franchisor, a vendor, someone who needs to click an approval
link from their own inbox — without settling that.

`render.yaml` in the repo root is the blueprint. Everything below is the part
Render cannot infer.

---

## 0 · What must exist first

- **A git remote.** Render deploys from GitHub, GitLab or Bitbucket. This repo
  had no remote at all for its first seven sessions; see step 1.
- **A Supabase project**, already stood up: `docs/SUPABASE.md`.
- **A Resend key**, if mail is to leave the outbox.

## 1 · The repository

The whole history is local. Create an **empty** repo on GitHub — no README, no
.gitignore, or the first push conflicts — then:

```bash
git remote add origin git@github.com:<owner>/<repo>.git
git push -u origin master
```

**Make it private.** Nothing secret is committed — `.env*` is gitignored and
`render.yaml` carries no values — but this is client work for a named pilot
brand, and the decisions log is candid about what is unfinished.

Two things to fix before the first push, because they travel with every commit:

- `git config user.email` is the placeholder `your-github-email@example.com`.
- The default branch is `master`. GitHub will not mind; a later `main` rename
  is a one-liner and is easier before anyone clones it.

## 2 · The service

**New → Blueprint**, point it at the repo, and Render reads `render.yaml`. It
will ask for every `sync: false` variable; that is the point of them.

Region is **Singapore** in the blueprint, deliberately: Supabase for this project
is in ap-northeast-1 (Tokyo) and Render has no Tokyo region. Oregon adds roughly
150ms to every query and a page here runs several in sequence. If the Supabase
project ever moves, move this with it.

### The variables, and the two that break quietly

| Variable | Value |
|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | from Supabase → Project Settings → API |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | the publishable key |
| `SUPABASE_SERVICE_ROLE_KEY` | the secret key — server only |
| `SUPABASE_STORAGE_BUCKET` | `request-files` |
| `DATABASE_URL` | the **session** pooler string, port 5432 |
| `RESEND_API_KEY` | from Resend |
| `RESEND_FROM_EMAIL` | an address on a verified domain, or `onboarding@resend.dev` |
| `APP_URL` | **`https://<service>.onrender.com`** — set after the first deploy |
| `CRON_SECRET` | generated by the blueprint |

**`APP_URL` is the one that fails silently.** Every approval link, franchisee
status link, budget-sheet link and corporate dashboard link in every message is
built from it. Left at its local default the mail still sends, still looks
right, and every link in it points at a laptop that is not there. Set it as soon
as Render assigns the hostname, and redeploy.

**`SUPABASE_STORAGE_BUCKET` is the one that loses data.** Render's filesystem is
ephemeral. Unset, the app selects the local-disk driver and writes a franchisee's
site photo and lease exhibit into a container that is discarded on the next
deploy. `src/lib/storage/index.ts` refuses to fall back for exactly this reason,
so an unset bucket fails loudly at the first upload rather than quietly at the
first redeploy — but it still has to be set.

## 3 · Tell Supabase about the new origin

**Auth → URL Configuration → Redirect URLs**: add

```
https://<service>.onrender.com/auth/callback
```

Without it GoTrue silently downgrades the magic link to the Site URL and sign-in
lands on the wrong page with the credential in a fragment the server never sees.
It fails in a way that looks like the app is broken; it is configuration.

Consider setting **Site URL** to the Render origin too, if this becomes the
environment people actually use.

## 4 · The review SLA

`/api/cron/review-sla` is a plain HTTP route on purpose — Vercel Cron drives it
in production, `npm run sla` drives it on a laptop, and on Render it is a cron
job running one `curl` with the `CRON_SECRET` bearer token.

**Render's cron jobs are not on the free tier** — check current pricing before
relying on the blueprint's cron service. Until then, run `npm run sla` by hand.
Nothing is ever approved by a clock (SPEC §3.1 and the Session 4 decisions), so a
missed run delays a reminder; it does not decide anything.

## 5 · What the free tier does

A free web service **spins down after inactivity**, and the next request pays a
cold start of roughly a minute. Fine for "have a look at this"; poor for a live
demo in front of a franchisor. Warm it with a request a few minutes before, or
put it on a paid instance for the day.

## Before showing it to anyone

`docs/QA.md` is the manual pass — the demo storyline, all five participants,
about 25 minutes. Run it **against the deployed URL**, not localhost. Two things
only a real deploy can get wrong, and both are invisible until someone clicks:

1. The links in the mail point at the deployment (that is `APP_URL`).
2. An uploaded file is still there after a redeploy (that is the bucket).

`npm run smoke` does not run against a deployment: it drives the dev sign-in
picker, which a Supabase-configured environment does not render (DECISIONS #106).
